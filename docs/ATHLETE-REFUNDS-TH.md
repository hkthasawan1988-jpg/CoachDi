# บัญชีคืนเงินนักกีฬาและโค้ชแนะนำ

ทำต่อใน Branch `fix/booking-alert-and-android-target-sdk` และ PR #3 ตามคำขอผู้ใช้ ไม่มีการ Deploy Production หรือ Merge main

## พฤติกรรม

- สมัครนักกีฬา: กรอกบัญชีภายหลังได้ ถ้ากรอกบางช่องต้องกรอกธนาคาร ชื่อบัญชี และเลขบัญชีให้ครบก่อนสมัคร
- โปรไฟล์นักกีฬา: เพิ่มปุ่มจัดการบัญชีรับเงินคืน ไม่เปลี่ยนการบันทึกชื่อ รูป หรือ Login เดิม
- รายการที่โค้ชปฏิเสธ/ยกเลิก: มีปุ่มโค้ชอื่น / การคืนเงิน และแสดงรายการที่เกี่ยวข้องบนหน้าแรก
- โค้ชแนะนำ: กีฬา วัน เวลาเต็มช่วง และสนามเดียวกัน ตรวจเวลาสอน วันหยุด นัดที่เผยแพร่ คลาสกลุ่ม รายการจองที่นักกีฬามีสิทธิ์เห็น และเวลาเผื่อเดินทาง ตัดโค้ชเดิมรวมบัญชี alias ออก ตรวจซ้ำเมื่อกดเลือก
- ตารางส่วนตัวของลูกค้าคนอื่นอ่านไม่ได้ จึงแสดงว่า “ไม่พบนัดชนในตารางที่เปิดเผย · รอโค้ชยืนยัน” ไม่มีการรับประกันความว่างหรือสร้าง Booking อัตโนมัติ การเลือกเปิดตารางเดิมเพื่อให้นักกีฬาตรวจเวลา ระยะเวลา และราคาแล้วส่งคำขอเอง
- หากอ่านตารางไม่ได้ ไม่แนะนำโค้ชรายนั้น หากไม่พบสนาม/เวลาที่ตรง แสดงให้เลือกวันหรือสนามใหม่
- ขอคืนเงิน: โหลดรายการล่าสุด บังคับธนาคาร ชื่อ เลขบัญชี และ Checkbox ยืนยัน ส่งผ่าน transaction ที่ Booking ID เดิม ป้องกันกดซ้ำ/หลายแท็บ พร้อมอ่านสถานะซ้ำเมื่อ transaction retry
- คำขอกรณีโค้ชยกเลิกเก็บสถานะยกเลิกเดิมและข้อมูลการชำระเดิม การส่งคำขอไม่เท่ากับชำระคืน
- ยกเลิกโดยนักกีฬา: ยังคงแบ่งภายใน/นอก 24 ชั่วโมง ใช้เวลาไทยและนาทีจริง ทั้งสองกรณีที่มีข้อมูลการชำระต้องแนบบัญชี รายการยังไม่ชำระยกเลิกได้โดยไม่สร้างคำขอคืนเงิน
- โค้ชตรวจบัญชีจากรายการของตน แนบหลักฐานหลังโอนจริง หรือใช้ขั้นตอนคืนเหรียญเดิม ไม่มีคำสั่งโอนเงินจริงเพิ่มเข้ามา

## ข้อมูลและสิทธิ์

บัญชีในโปรไฟล์อยู่ที่ `users/{uid}/refundAccount` ประกอบด้วย `bank`, `accountName`, `accountNumber`, `updatedAt` เลขบัญชีเป็น string รักษาศูนย์นำหน้า รองรับเลขไทยและขีด/ช่องว่าง ข้อมูลนี้อ่านได้เฉพาะเจ้าของและ Admin ตามสิทธิ์ users เดิม

สำเนาสำหรับรายการใช้ฟิลด์เดิม `bookings/{id}/refundBank`, `refundAccountName`, `refundAccountNumber` เพิ่ม `refundRequestedAt`, `refundRequestedBy`, `refundStatus: requested`, `refundReviewRequired` เฉพาะรายการที่ขอคืน โค้ชคู่รายการและ Admin อ่านได้ตามสิทธิ์ Bookings เดิม ไม่ใส่เลขบัญชีใน Notification, Chat, public profile, localStorage หรือรายงานทดสอบ

Rules เพิ่มการตรวจรูปแบบบัญชี จำกัดผู้เริ่มคำขอให้เป็นเจ้าของ Booking และคงข้อมูลบัญชีที่ส่งแล้วไว้สำหรับตรวจสอบ โค้ชเปลี่ยนหรือเอาบัญชีออกจากคำขอไม่ได้ ส่วน Admin แก้ไขได้ตามสิทธิ์เดิม ห้ามโค้ชลบรายการที่มีหลักฐานชำระ/คำขอคืนเงิน

การแก้ Rules อยู่ใน PR เท่านั้น ก่อนนำขึ้นจริงต้องตรวจ Rules ปัจจุบันใน Firebase Console และนำเฉพาะส่วนที่รีวิวแล้วไปปรับ ไม่ใช้ไฟล์ Rules เก่าทับ Production โดยไม่เปรียบเทียบ

ตรวจ Console แบบอ่านอย่างเดียวเมื่อ 7 กันยายน 2026 แล้วพบว่า Production มีเงื่อนไขอนุมัติโค้ชและตรวจไฟล์สลิปเพิ่มเติมจาก Repository ส่วน users/refundAccount ยังอ่านได้เฉพาะเจ้าของ/Admin ตามกฎระดับ users เครื่องมือ `node scripts/prepare-refund-rules.cjs CURRENT_EXPORT.json REVIEW_OUTPUT.json` ช่วยเพิ่มเฉพาะส่วนบัญชีลงในไฟล์ Rules ปัจจุบันที่ผู้ดูแล Export มา โดยเก็บกฎเดิมทุกส่วนและไม่ Deploy ต้องรีวิว diff และรัน Emulator กับไฟล์ที่รวมแล้วก่อนเผยแพร่ Rules จริง

## ทดสอบ

`npm run build`, `npm run check`, `npm run test:unit`, `npm run test:rules`, `npm test` และ Android `:app:connectedDebugAndroidTest` ใน GitHub Actions

Firebase Rules ใช้ Emulator project `demo-coach-di-refunds` บน localhost เท่านั้น Web tests ปิดเครือข่ายภายนอกและใช้ข้อมูลสมมติ Native tests เปิดฟอร์มบน Android WebView โดยไม่สมัคร/ชำระจริง ผลและ Artifact ของ revision ที่ทดสอบบันทึกใน PR และรายงานส่งมอบ

Android versionCode เพิ่มจาก 1 เป็น 2 ใช้ applicationId/namespace/SDK/JDK/signing configuration เดิม ไม่มี Production deploy อัตโนมัติ

## UAT ที่ยังต้องทำก่อน Release

ผู้ใช้ระบุเครื่อง Samsung Galaxy Z Fold7 แล้ว ต้องติดตั้ง APK ของ revision ที่ผ่าน CI ทดสอบจอพับ/กาง การหมุน คีย์บอร์ด Android Back เลือกไฟล์สลิป กลับจากแอปธนาคาร และ Login จริง

ธุรกรรมจริงยังต้องระบุโค้ช วันเวลา สนาม และวงเงินสูงสุดก่อนดำเนินการ ต้องทดสอบการจอง การชำระ การยกเลิกทั้งสองฝ่าย การแนบบัญชี การตรวจ/โอนคืน และตรวจว่าไม่มีรายการหรือยอดซ้ำ ให้ผู้ใช้โอนผ่านแอปธนาคารของตน ไม่มีการสร้างสลิปปลอมหรือแก้สถานะ Production เพื่อแทนหลักฐานจริง

พบ App Check reCAPTCHA warning ใน Android รุ่นก่อน โดย Firebase Authentication และ Realtime Database อยู่ใน Monitoring ต้องตรวจ Login/DB ของ APK บนเครื่องจริง ไม่ปิดระบบตรวจสอบเพื่อให้ UAT ผ่าน
